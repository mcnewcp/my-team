# The App JWT is signed in process, with no dependency and no third binary

`gh` cannot authenticate as a GitHub App — it sends `Authorization: token`, and an App identity
needs a `Bearer` JWT signed with the App's private key — so the orchestrator mints that JWT
itself. It is signed with about eighty lines of standard library in
[`core/app_jwt.py`](../../src/my_team/core/app_jwt.py): PKCS#1 v1.5 over SHA-256, a DER walk to
pull the modulus and private exponent out of the PEM, and `pow`.

Hand-written signing is a thing to justify rather than a thing to do lightly, and the
justification is that the alternatives each cost something this design has already decided not
to spend — while the specific hazards of writing it are, here, not in play.

## Considered options

**A dependency — `PyJWT`, or `cryptography`.** `pyproject.toml` declares no runtime dependencies
at all, deliberately: the orchestrator shells out to `gh` and to a harness binary, and the pure
core is plain data over the standard library. `cryptography` is a wheel with a compiled Rust
extension, which is a real install-time cost and a real supply-chain surface for one signature
per role per run. `PyJWT` is pure Python but still needs `cryptography` for RS256, so it buys an
import and not an install.

**`openssl dgst -sha256 -sign`.** The wizard already does exactly this, and in a shell script it
is the right answer. In the package it is not: it puts a third binary on the critical path, and
`doctor`'s blocking list is the two the spec names — `gh` and the harness. Adding a check widens
the spec; not adding one means a missing `openssl` surfaces as a role failure that blames the
key.

## Consequences

**The two hazards usually worth fearing in hand-written signing are absent.** RSASSA-PKCS1-v1_5
is deterministic and consumes no randomness, so there is no nonce to get wrong. The key is one
the process already holds and the arithmetic runs locally against no attacker-supplied input, so
a timing side channel has nothing to leak to. What remains is the ordinary risk of getting the
DigestInfo prefix, the padding or the DER walk wrong — a bug that fails loudly on first contact
with GitHub rather than silently.

**So the signer is checked against a real implementation, never against itself.** In
[`tests/test_app_jwt.py`](../../tests/test_app_jwt.py) — the suite that asks what a signature is
worth — every key is generated by `openssl` and every signature the module produces is handed back
to `openssl dgst -verify`. A test that verified with the same big-integer arithmetic that signed
would establish only that the code agrees with itself, which is precisely the failure worth ruling
out. Both PEM encodings are covered: GitHub downloads PKCS#1, and a key that has been through a
modern `openssl` comes back PKCS#8.

**That rule is about the signer's own suite, and deliberately not about every suite.** The tests
above the signer — credentials, probe — assert which file was read, what the failure paths name,
and where a token may travel; none of them asserts that a signature is sound. They need bytes that
reach the signer and nothing more, so they use the parseable non-key `tests/conftest.py` builds: a
real PEM committed to a repo is secret-scanner bait for no gain, and generating one per session
spends `openssl genrsa` on a signature nothing verifies. Stating the rule unqualified would have
made this record false about the suites it did not mean.

**It is proven end to end against GitHub, not only against `openssl`.** `my-team doctor` resolves
all three provisioned Apps — the key signs, GitHub accepts the JWT, and each installation
resolves — which is a stronger statement than any unit test can make.

**Reversing this is cheap.** The module is one function behind one signature, `app_jwt(pem, *,
app_id, now)`. If the standard library ever grows an RSA signing API, or the dependency budget
changes, the swap touches one file and no caller.

## Problem Statement

A solo maintainer with a well-specified backlog can only move one issue at a time, and each one
costs a full session of attention: read the issue, drive an agent through the implementation,
read the diff, decide what actually needs fixing, drive another round, merge. The agent does the
typing; the human does the sitting there.

The work is already legible enough to hand off — issues are triaged, CI is green or it isn't, a
diff either does what the issue asked or it doesn't — but there is nothing that will pick up a
labelled issue and carry it to a merged pull request unattended. Existing tools stop at the
session boundary: they make one agent turn better, not a development loop autonomous.

Three things make that loop hard rather than merely tedious:

- **An agent's account of its own work is not evidence.** Both harnesses in scope exit `0` on a
  failed task — Codex when the model tries and gives up, Claude Code when a tool is blocked and
  the failure survives only as English prose. Anything that trusts a self-report will report
  success on work that did not happen.
- **A crash must not lose the run.** An unattended loop that keeps its progress in memory has to
  be restarted from the beginning, by a human, which is the thing being automated away.
- **Nothing stops it.** A review-and-revise cycle with no termination condition spends real
  budget forever, and the failure mode that costs most is not a crash but a livelock, where every
  step succeeds and no progress is made.

## Solution

`my-team` is a thin, locally-running orchestrator installed into a **target repo** and run from
its root. `my-team work <issue>` drives one `ready-for-agent` issue through implement → pull
request → review → judge → revise → merge, unattended, and exits when the pull request merges or
when it needs a human.

Four properties carry the whole design:

1. **GitHub is the sole source of truth for orchestrator state.** The orchestrator holds nothing
   durable. Every **tick** — one **Observation**, one **Action**, exit — re-derives where the
   issue sits from what GitHub reports. Killing the process loses nothing, and the resume path is
   the same code as the first run.
   ([ADR 0009](../adr/0009-github-is-the-sole-source-of-truth.md))

2. **Verify by observation.** A **State** is never advanced on an agent's word when the fact is
   checkable directly. The **trust boundary** is exactly two **Declarations** — the implementer
   marking its pull request ready, and the judge submitting a formal review — both deliberate API
   calls attributable to a **role** identity. **No prose is parsed anywhere in the state machine.**
   ([ADR 0010](../adr/0010-verify-by-observation.md))

3. **Roles are identities, not jobs.** Three GitHub Apps — implementer, reviewer, judge — each
   holding its own credential and its own permissions. Role authority lives where GitHub enforces
   it, so a reviewer agent with unrestricted tools still cannot push: the token 403s.

4. **The payload is the product.** The five procedures the loop runs ship into the target repo as
   ordinary skills, so the repo stays self-describing and a human can run `/mt-implement 17` by
   hand and get identical behaviour minus the orchestration.

**Acceptance:** standing in `mcnewcp/personal-assistant`, `my-team work <issue>` takes one
`ready-for-agent` issue through the full loop to a merged pull request with no human
intervention, with `--require-approval-to-merge` available.

## User Stories

### Running the loop

1. As a product owner, I want to label an issue `ready-for-agent` and run one command against it,
   so that a full implementation round happens without me sitting through it.
2. As a product owner, I want the loop to exit rather than poll whenever it is waiting on me, so
   that a parked run costs nothing and tells me it is my turn.
3. As a product owner, I want a distinct exit code for merged, error, escalated, awaiting-approval
   and halted, so that a wrapper script can tell "something went wrong" from "your turn" without
   parsing output.
4. As a product owner, I want to kill the process at any moment and re-run the same command, so
   that the loop resumes from where the repo actually is rather than from where it thinks it was.
5. As a product owner, I want `--require-approval-to-merge`, so that I can keep the final gate for
   myself while the rest of the loop runs unattended.
6. As a product owner, I want to run the loop from any machine with the repo and my keys, so that
   a run is not tied to the laptop that started it.
7. As a product owner, I want a single tick I can run on demand, so that I can step the machine by
   hand when I am debugging it.
8. As a product owner, I want the terminal to show which state was derived, which row selected it
   and what the agent is doing, so that I can watch the loop reason rather than guess.
9. As a product owner, I want that terminal output to stay readable when redirected to a file, so
   that a long unattended run leaves a log I can read afterwards.
10. As a product owner, I want context occupancy shown per activity line against the **smart zone**,
    so that I can see a dispatch climbing toward its stop.

### Getting set up

11. As a product owner, I want one `init` command that writes the config and the payload and tells
    me the one commit to make, so that setup is a single step rather than a checklist.
12. As a product owner, I want `init` never to touch my `CLAUDE.md`, my `AGENTS.md`, my merge
    policy or my branch protection, so that installing the tool does not silently reconfigure my
    repo.
13. As a product owner, I want `doctor` to check every precondition the loop depends on and tell me
    exactly which one is unmet, so that a misconfiguration fails before a run rather than during one.
14. As a product owner, I want `doctor` to verify the payload is *committed on the default branch*
    rather than merely present on disk, so that I find out about an unpushed payload before a tick
    silently dispatches an unrecognised slash command.
15. As a product owner, I want `doctor` to report my branch protection and warn about the two
    settings that surprise people, so that I can decide what to configure without the tool
    configuring it for me.
16. As a product owner, I want `doctor` to confirm my repo is squash-merge-only with
    auto-delete-on-merge, so that the one-pull-request-one-commit assumption the conventions rest
    on actually holds.
17. As a product owner, I want a wizard for the browser-only parts of provisioning a role App, so
    that the ~28 clicks per role are guided rather than remembered.

### The skill payload

18. As a product owner, I want to run the same procedure the loop runs by hand, so that the tool is
    not a black box and I can take over any step.
19. As a product owner, I want payload skills under names nothing else claims, so that a personal
    skill in my home directory cannot silently shadow the one my repo installed.
20. As a product owner, I want `sync` to refuse to touch a file it did not write, so that my own
    edits are never clobbered.
21. As a product owner, I want `eject` to hand me ownership of a skill without moving any files, so
    that overriding one procedure does not fork the whole payload.
22. As a product owner, I want `sync --check` to exit non-zero when the installed payload has
    drifted, so that my CI can gate on it.
23. As a product owner, I want a skill dropped from a future payload to be removed from my repo, so
    that dead procedures do not accumulate.
24. As a product owner, I want the payload installed under both skill roots, so that adding a second
    harness later is not a migration across every repo that has it.

### Implementation

25. As an implementer, I want the branch and worktree created for me before I am dispatched, so that
    naming mechanics are not my judgment call.
26. As an implementer, I want to work in a directory that is not the human's checkout, so that a long
    unattended run does not lock them out of their own repo.
27. As an implementer, I want my work pushed even if I crash mid-round, so that the next session
    resumes from the branch rather than from nothing.
28. As an implementer, I want to be told which checks are the gate, so that "run the repo's checks"
    is concrete without a skill naming a tool.
29. As an implementer, I want the pull request opened for me with a lint-safe placeholder, so that I
    do not have to invent a conventional-commit title before the work exists.
30. As an implementer, I want one unambiguous act that means "this round is finished", so that the
    orchestrator never has to guess whether I stopped or handed off.
31. As an implementer, I want to be told plainly never to mark ready to escape a problem, so that
    the declaration the whole trust boundary rests on stays honest.
32. As an implementer, I want the reviewer's list handed to me as context rather than instruction, so
    that I do not bypass the only actor allowed to say a point is not blocking.
33. As an implementer, I want a stated precedence — red CI, then the judge's necessary-now points,
    then the issue — so that an undifferentiated picture does not become an arbitrary one.
34. As an implementer, I want to check the branch against its base and rebase when it conflicts, so
    that ordinary interference is ordinary work rather than an escalation.
35. As an implementer, I want my closing report posted to the pull request conversation, so that a
    flagged deviation or an admitted guess reaches the reviewer instead of dying in a log file.

### Review and judgment

36. As a reviewer, I want the whole diff every round rather than the delta, so that a change that
    breaks something reviewed clean two rounds ago is still caught.
37. As a reviewer, I want to report everything I find without ranking or self-censoring, so that the
    filtering is done by the actor with no stake in my list.
38. As a reviewer, I want my own prior reviews and the judge's disposals of them, so that re-raising
    a dropped point is a deliberate act rather than an inevitability.
39. As a reviewer, I want to review against the repo's own documented standards first and the idiom
    of the surrounding code second, so that my findings are about this codebase rather than about
    my defaults.
40. As a reviewer, I want to read CI rather than re-run it by default, so that I am not re-
    establishing a fact the dispatching guard already established.
41. As a judge, I want the pull request, the reviewer's review, the issue and the code, so that I can
    rule on the review and on what I can see for myself.
42. As a judge, I want exactly three **disposals** and no non-blocking fourth, so that every point
    has a recorded fate and nothing accumulates in a bucket nobody reads.
43. As a judge, I want to publish a **disposal ledger** naming each point and its fate, so that
    "every point gets exactly one disposal" is checkable by a human reading the thread.
44. As a judge, I want to be told what my approval actually does under the current flags, so that I
    am not hedging about the consequence of my own declaration.
45. As a judge, I want to escalate on judgment when an issue is unworkable, so that an
    underspecified issue does not burn eight rounds to deliver a message I could write immediately.
46. As a judge, I want to file the issues I am keeping *before* I submit my verdict, so that nothing
    is left unwritten after the act that takes the decision out of my hands.

### Continuity

47. As any role, I want to be stopped at the **smart zone** rather than at the context ceiling, so
    that my successor inherits a working context instead of a rotted one.
48. As any role, I want to write a **handoff** carrying what was tried and rejected, what was next,
    and what the artifacts do not record, so that my successor does not re-derive it.
49. As any role, I want my successor to start in a brand-new session with the handoff available, so
    that resuming does not reload the very context the stop existed to escape.
50. As a product owner, I want a missing handoff to be a slower successor rather than an error, so
    that losing a local file never wedges a run.

### When it does not converge

51. As a product owner, I want four derived limits — judge rounds, CI-repair heads, implementation
    rounds and elapsed time — so that no cycle in the loop is unbounded.
52. As a product owner, I want every limit counted from my own most recent re-authorization, so that
    clearing an escalation actually clears it rather than tripping the same limit on the first tick.
53. As a product owner, I want an escalation comment carrying the tripped limit, the evidence, links
    to the specific artifacts and the agent's own last words, so that I can act without
    reconstructing what happened.
54. As a product owner, I want escalation to swap `ready-for-agent` for `ready-for-human`, so that an
    escalated issue stops matching every "ready for an agent" query.
55. As a product owner, I want to reply in the thread and swap the labels back, so that resuming is
    one act that both re-authorizes the issue and resets the counters.
56. As a product owner, I want my guidance in that thread to reach the next agent, so that a
    mid-run correction lands without stopping the loop.
57. As a product owner, I want the loop to halt quietly — not escalate — when I close the issue,
    remove the label or close the pull request, so that it does not shout for a human who is
    already acting.
58. As a product owner, I want a stalled or hung dispatch caught by elapsed time, so that an agent
    that never returns is still bounded.
59. As a product owner, I want failure backoff inside a run, so that a dispatch failing in five
    seconds does not spin hundreds of times before the stall detector notices.
60. As a product owner, I want my workspace left intact on a crash and deleted only on merge or on
    an explicit `clean`, so that nothing silently deletes work.

### Trust

61. As a product owner, I want an issue admitted to the loop only when a **trusted human** applied
    the label, so that a world-writable tracker is not a world-writable instruction surface.
62. As a product owner, I want authorization to lapse when the body is edited by an untrusted editor
    afterwards, so that an issue cannot be vouched for and then rewritten.
63. As a product owner, I want trust derived from GitHub on every read rather than listed in config,
    so that adding a collaborator this morning does not require editing a file.
64. As a product owner, I want no App to count as a trusted human — our own roles included — so that
    an agent can propose work and never authorize it.
65. As a product owner, I want an outsider's formal review to be invisible to the machine rather
    than ambiguous to it, so that a passerby cannot park my loop.

### Building and testing the tool

66. As a maintainer, I want the ladder expressed as data, so that a test can assert every row has a
    case and a twentieth row cannot slip in untested.
67. As a maintainer, I want the state function to take no client, so that it cannot do I/O even by
    accident.
68. As a maintainer, I want a loop-level property test asserting no tick derives the same state twice
    unless the world changed, so that a livelock is caught by the suite rather than by a human
    watching it spin.
69. As a maintainer, I want a contract test binding my fakes to real captured payloads, so that a
    builder cannot quietly reproduce a belief that is wrong.
70. As a maintainer, I want a fixture repo with steerable CI, so that the three check-run states can
    be constructed against real check runs.
71. As a maintainer, I want nothing an agent wrote ever asserted on, so that the suite never becomes
    a quality score for a model.

## Implementation Decisions

### 0. Shape, language and packaging

- **Python + `uv`**, installed with `uv tool install my-team` and run from the **target repo**
  root — so `gh` infers the repo and the harness picks up project context for free. Textual is
  the growth path to a board/inbox view; v0.1 ships no TUI.
- **Two repos are always in play.** The **orchestrator repo** (`mcnewcp/my-team`) is the tool's
  own source; the **target repo** is what it is pointed at. Since all three role Apps are
  installed on both, the orchestrator repo is *also* a target repo.
- **Three I/O ports and a pure core.** ([#12](https://github.com/mcnewcp/my-team/issues/12))

  | Port | Direction | Notes |
  | --- | --- | --- |
  | GitHub | read + write | split into `fetch` (all I/O) and `parse` (pure) |
  | Harness | write | one call per **Action**, see §3 |
  | Local git | **write-only** | worktree create/remove, sweep push — never read back |

  The local-git port is write-only because the workspace is **acted on and never observed**
  ([ADR 0001](../adr/0001-isolated-worktree-and-handoffs-outside-git.md)). Its fake need only
  record calls.

- **The pure core is two functions over one Observation**, neither of which makes an API call:

  ```
  derive(observation, now, work_started_at) -> State
  assemble(observation, action, handoff_dir) -> Briefing
  ```

  Config is applied at **parse**, not inside either function.

### 1. The CLI surface and `.my-team/config.toml`

#### Commands

| Command | Does |
| --- | --- |
| `my-team init` | One step: writes `.my-team/config.toml` (prompting for `product_owner`, authenticated user pre-filled), writes the payload into both skill roots, writes the manifest, **creates the `ready-for-agent` and `ready-for-human` labels if absent**, prints **one commit line**. Never mutates merge policy, branch protection, `CLAUDE.md` or `AGENTS.md`. |
| `my-team sync` | Reconciles the installed payload against the package (six cases, §4). Does **not** commit. |
| `my-team sync --check` | Same computation, writes nothing, exits non-zero if any case would act or refuse. The CI gate, and what `doctor` calls. |
| `my-team eject <skill>` | Sets `ejected: true` on the manifest entry. No file moves. |
| `my-team doctor` | Checks every precondition; blocking checks fail, advisory checks warn. |
| `my-team work <issue>` | The loop. Ticks until a terminal state or a human wait. |
| `my-team clean <issue>` | Tears down an abandoned issue's **workspace**. The only thing that deletes work, and it is explicit. |

`work` flags: `--require-approval-to-merge` (gates the mechanical merge on a trusted human's
`APPROVED` as well as the judge's), `--once` (perform exactly one tick and exit — the `tick`
primitive, exposed for debugging and for the release rehearsal).

#### Exit codes

| Code | Meaning |
| --- | --- |
| `0` | merged |
| `1` | error — including `HarnessError`, which ends the run rather than the tick |
| `2` | escalated |
| `3` | awaiting human approval |
| `4` | halted (issue closed, label removed, or pull request closed unmerged) |

Each prints why, because the likeliest way a human meets one is running `work` on an issue that is
already parked.

```toml
# Keys are role-named; App names are not. Nothing keys on a slug.

[roles.reviewer]

[roles.judge]

key_path        = "~/.config/my-team/keys/judge.pem"
```

**Deliberately absent**, each because someone will later mistake it for an oversight:

- **`trusted_humans`** — dropped by [#25](https://github.com/mcnewcp/my-team/issues/25). Trust is
  `authorAssociation ∈ {OWNER, MEMBER, COLLABORATOR}`, read off the payload it already arrives on.
  A login list drifts against the real collaborator list and cannot express "we added a
  collaborator this morning."
- **A per-role tool allowlist** — dropped by [#10](https://github.com/mcnewcp/my-team/issues/10).
  It is a worse copy of a boundary that already exists in the credential, it enforced a role
  boundary silently at exit `0`, and under it an agent effectively cannot use shell variables.
- **`trusted_apps`** — an empty key is code with no second branch.
- **A budget ceiling in money** — `total_cost_usd` is list price and not spend under a
  subscription, so the only cost figure the harness reports can never be a gate.
- **The ladder's row order, the progress-event set, which outcomes end the run, the backoff
  schedule and the escalation ritual.** Those are the machine; the numbers are the policy.

**Naming:** every limit is `max_*`. `cap` is already spoken for twice — as an `_Avoid_` term for
**smart zone**, and as the seam's own parameter — so a reader meeting "cap" in config would not
know which was meant.

⚠️ **The defaults are guesses.** `3, 3, 8, 90, 30, 15` want calibration against real runs.

#### `doctor`

**Blocking:**

1. `gh` present and authenticated; the harness binary present.
2. `.my-team/config.toml` present and parses; `required_checks` declared (empty is legal, and
   warned about).
3. `product_owner` set, and resolved against the `permission` API to `write` or `admin`. This is
   the one place the exact primitive is worth a round trip; without it a mistyped login makes the
   human's own guidance silently invisible to every prompt.
4. Three role entries; each key file present at mode `0600`; each installation resolves; each
   `bot_user_id` matches what the API reports.
5. The payload present **and committed on the default branch** — `sync --check` clean, and the
   `.claude/skills/mt-*` symlinks resolve.
6. The target repo is **squash-merge-only with auto-delete-on-merge**. Merge commits break the
   one-pull-request-one-commit assumption the commit conventions rest on.
7. The `ready-for-agent` and `ready-for-human` labels exist. They are the only two facts about an
   issue that are not derivable, so without them nothing can be authorized and nothing can be
   escalated to.

**Advisory — report, never block** ([#27](https://github.com/mcnewcp/my-team/issues/27)):

7. Report the default branch's protection.
8. ⚠️ Warn on `required_approving_review_count: 0` — it stops GitHub computing `reviewDecision`.
   Harmless to the ladder, which never reads that field, and thoroughly confusing to a human.
9. ⚠️ Warn when protection is present but `enforce_admins` is `false` — that configuration guards
   the pipeline and not the human.
10. Note `require_last_push_approval` as **unmeasured** if set.
11. Warn when `required_checks` is empty, since the CI gate is then vacuous.

**Protection is recommended, never required, and `init` never sets it.** The loop is provably
correct either way; requiring it would make the acceptance criterion contingent on reconfiguring a
target repo.

### 2. The tick state machine

**The machine describes the *issue*.** The issue number is the durable key, it exists before the
branch and before the pull request, and it is the argument to `work`. The pull request is derived,
singular and replaceable — and the first rows of the ladder exist precisely because the issue has
states the pull request cannot represent.

#### What one tick observes

| Source | Fields |
| --- | --- |
| Issue | `state`, `labels`, the latest `labeled: ready-for-agent` timeline event (actor and time), body `lastEditedAt` + `editor` |
| Branch | remote refs matching `my-team/<issue>-*` (**the count matters**), head SHA, commits ahead of base |
| Pull request | `state`, `isDraft`, `headRefOid`, `merged`, `mergeable`, `mergeable_state`, `reviews[]` (author numeric id, author type, state, `commit_id`, `submitted_at`), `closedByPullRequestsReferences` |
| Checks | check runs at head SHA, filtered to the config-declared required names |
| Timeline | `convert_to_draft` / `ready_for_review` events ordered by monotonic event id; **progress events** on GitHub's own clock |

⚠️ **The Observation carries no comment bodies.** Two tickets were separately about to add
trusted comments, role comments and review bodies to it purely to feed the prompt assembler —
which no longer needs them (§7). Nothing in the ladder parses prose.

Two things happen at **parse**, not in the ladder:

- **Untrusted reviews are dropped from the snapshot entirely.** A review from a `User` whose
  association is not `OWNER`/`MEMBER`/`COLLABORATOR` is not in the Observation at all, exactly as
  untrusted comments are absent from prompts.
- **Role identities are matched by numeric bot user id**, never by login. `gh` reports the author
  as `reviewer-my-team` while REST reports `reviewer-my-team[bot]`; a string comparison across
  those two surfaces silently matches nothing, and a trust predicate that silently matches nothing
  fails open in one direction and closed in the other.

Derived predicates, exactly two: `current(r) ≡ r.commit_id == pr.headRefOid`, and `ci_ok` ≡ every
config-required check green at head, empty list ⇒ true.

#### The ladder

**Nineteen rows, evaluated top-down, first match wins. The order *is* the ambiguity-breaker** —
it is part of the design, not an implementation detail, which is why the ladder is expressed as a
list of `(name, guard, action)` the tests can enumerate.

| # | State | Recognised by | Action | Then |
| --- | --- | --- | --- | --- |
| 1 | `ESCALATED` | `ready-for-human` present | none | exit 2 |
| 2 | `HALTED` | issue closed, or `ready-for-agent` absent, or PR closed-unmerged | none — workspace left intact | exit 4 |
| 3 | `UNAUTHORIZED` | no `ready-for-agent` label event by a trusted `User`, or the body edited by an untrusted editor since that event | escalate | exit 2 |
| 4 | `AMBIGUOUS` | >1 matching branch, >1 open PR, a **`Bot`** review from an App id not in config, or PR with zero commits ahead of base | escalate | exit 2 |
| 5 | `OBSERVATION_UNSETTLED` | `mergeable_state == "unknown"` | wait | poll |
| 6 | `MERGED` | PR merged | tear down workspace — terminal | exit 0 |
| 7 | `NOT_CONVERGING` | any of the four limits tripped | escalate | exit 2 |
| 8 | `UNSTARTED` | no matching remote branch | create worktree + branch off `origin/<default>`; dispatch **implementer `/mt-implement`**; **push** | next tick |
| 9 | `NO_PR` | branch has commits, no PR | mechanically open a **draft** PR under the implementer's identity — lint-safe placeholder title, body `Closes #<n>` | next tick |
| 10 | `IMPLEMENTING` | PR `isDraft` | dispatch **implementer `/mt-implement`**; **push** | next tick |
| 11 | `MERGEABILITY_UNSETTLED` | `mergeable` is `null` | wait | poll |
| 12 | `CONFLICTED` | `mergeable` is `false` | convert PR to draft | next tick |
| 13 | `CI_FAILED` | a required check failed at head | convert PR to draft | next tick |
| 14 | `CI_PENDING` | a required check unresolved at head | wait | poll |
| 15 | `NEEDS_REVIEW` | `ci_ok`, no current reviewer `COMMENT` | dispatch **reviewer `/mt-review`** | next tick |
| 16 | `NEEDS_JUDGMENT` | `ci_ok`, current reviewer review, no current judge verdict | dispatch **judge `/mt-judge`** | next tick |
| 17 | `REVISION_REQUIRED` | current judge `CHANGES_REQUESTED` | convert PR to draft | next tick |
| 18 | `NEEDS_HUMAN_APPROVAL` | current judge `APPROVED`, flag set, no current trusted-human `APPROVED` | wait — `@product_owner` narration on entry | exit 3 |
| 19 | `MERGEABLE` | current judge `APPROVED`, `ci_ok`, human approval if required | squash-merge with `--match-head-commit <head>` under the **judge's** identity | next tick → `MERGED` |

**The draft flag is the implementer's latch.**
([ADR 0002](../adr/0002-draft-flag-is-the-implementer-latch.md)) The orchestrator converts to
draft on every implementation dispatch — first pass, CI repair, conflict, judge revision — and
only the implementer converts it back. That is what makes "round complete" *repeatable* rather
than the one-shot signal pull-request creation could only ever give once, and it is why
`IMPLEMENTING` absorbs all four cases as one state. **It does not encode *why* it is implementing.**

Rows 12, 13 and 17 flip the latch and **stop**; the dispatch happens on the next tick via row 10.
Two mutations in one tick would buy one saved tick at the cost of a crash window, and ticks are
free.

#### The ladder's checking rule

**For every row whose action is a dispatch, the guard must be the negation of that action's
definition of done.** It does not claim an action always succeeds — row 10 re-firing on a
handed-off round is correct. It claims that re-firing is always a **retry**, never a livelock.

| Row | Guard | Dispatched action's definition of done | Same fact? |
| --- | --- | --- | --- |
| 8 `UNSTARTED` | no remote branch | branch on origin | ✅ (via the sweep push) |
| 10 `IMPLEMENTING` | `isDraft` | mark the PR ready | ✅ |
| 15 `NEEDS_REVIEW` | no current reviewer `COMMENT` | post a `COMMENT` review | ✅ |
| 16 `NEEDS_JUDGMENT` | no current judge verdict | submit a formal review | ✅ |

Rows that mutate mechanically (9, 12, 13, 17, 19) discharge deterministically; rows that wait
(5, 11, 14, 18) discharge externally. This rule caught both defects a real run surfaced and
nothing else, which is why it is adopted as the ladder's checking rule rather than as two patches.
It binds the skills too: each skill's *stated* definition of done must name the same fact its
dispatching row's guard reads.

#### Pacing

- **Poll `poll_interval` (15s)** on rows 5, 11, 14 — machine waits that resolve on their own. 15s
  clears the measured ~10s head-SHA lag in one hop.
- **Exit** on rows 1, 2, 6, 18, and on every row whose action is *escalate* (3, 4, 7). There is no
  point polling for a human.
- **A tick that dispatched needs no sleep** — the dispatch was the pacing. A tick that mutated
  mechanically has work to do immediately.
- **Backoff on failure:** after `Failed` or `TimedOut`, 30s → 60s → 120s, capped at 300s, reset by
  any `Finished` or `Capped`. Without it a dispatch that fails in five seconds spins ~700 times
  before the 90-minute stall detector notices. Ephemeral, inside one `work` invocation, and it
  never selects an action.
- **No rate-limit adaptivity.** An installation token allows 5000 requests/hour and a tick costs
  roughly eight, so 15s polling runs at ~1900/hour. Honouring `Retry-After` belongs to the GitHub
  client, not to loop policy.

#### What breaks each tie

- **"Finished the round" vs "committed halfway and handed off"** — the central ambiguity. Broken
  by `isDraft`, repeatable once per round. A handoff cannot break it; handoffs are never an input
  to a decision.
- **Two states that both look reviewable** — broken by ladder order, not by extra predicates.
- **A review describing a tree that no longer exists** — broken by comparing the review's pinned
  `commit_id` to the current head. ⚠️ **Never by reading review state.** Measured: under
  dismiss-stale a push rewrites the review to `DISMISSED` and the platform agrees; with
  dismiss-stale *off* the same push leaves it `APPROVED` at the stale SHA with
  `mergeStateStatus: CLEAN` — **GitHub will merge unreviewed code**; and enabling the rule
  retroactively gates correctly while still reporting `APPROVED`. A machine reading `state` is
  wrong in two of three cases.
- **"CI has not started" vs "there is no CI"** — indistinguishable from the check rollup, so it is
  not inferred. Config declares the names; an empty list means no gate. A grace timer would be a
  race dressed up as a policy.
- **A stale head SHA making a stale review look current** — row 5. A push takes several seconds to
  surface, and during that window `mergeable_state` reads `"unknown"`.
- **Anything mapping to more than one state** — row 4. Fail closed, never guess.

#### Representation on GitHub

**`docs/agents/triage-labels.md` needs no extension.** `ready-for-agent` and `ready-for-human`
carry the only two facts that are not derivable — **authorization** and **escalation** — and
everything else comes off the branch glob, pull request state, `isDraft`, review authorship, SHA
comparison, check runs and timeline events.

**The reviews list accumulates**, so filtering by numeric uid must take the **latest by SHA**, not
any match.

⚠️ **`reviewDecision` is never read**, and neither is any other field GitHub derives on our behalf.
It reads `null` on a repo with a fresh `APPROVED` plainly in the list whenever a protection rule
sets `required_approving_review_count: 0`. A machine gated on it would refuse to merge and give no
reason.

⚠️ **`mergeStateStatus: CLEAN` on a draft is a lie** — stable across reads, and merging anyway
returns `405 "still a draft"`. `isDraft` must be checked before that field is read as a merge
gate. Structurally satisfied here, because row 10 catches every draft above row 19.

**Read `mergeable`, never `mergeable_state`,** for conflict detection: `mergeable_state` conflates
a conflict with protection state and reports `"draft"` for any draft. Placing both conflict rows
*below* `IMPLEMENTING` is what makes that safe — whatever GitHub reports for a draft is then
irrelevant.

#### Human interference

- **Pull request closed unmerged**, **issue closed mid-flight**, **`ready-for-agent` removed
  mid-run** → **halt**, workspace untouched. Halt, not escalate: escalation shouts for a human who
  is not there, and in all three cases the human is already here.
- **A half-cleared escalation** (`ready-for-human` removed without `ready-for-agent` restored)
  matches row 2 and halts. Correct — an issue with neither label is untriaged — but quiet, so
  `work` says so on exit.
- **A commit on the branch the implementer did not author** → **no handling at all.** The new SHA
  invalidates every review by the staleness rule, and the implementer re-reads the tree each
  session.
- **An edited issue body** needs no handling either, since every dispatch re-reads it — except as
  authorization, which row 3 owns.

### 3. The harness seam, and the narration seam

**The seam's unit is an *Action*, not a process.** A capped dispatch is *run → stop signal →
resume to write the handoff*, and the seam swallows that whole behind one call, because the stop
signal is harness-specific (SIGTERM on Claude Code; Codex is SIGINT-only with no SIGTERM handler)
and that is exactly the detail the seam exists to hide.

**What the seam has never heard of:** roles, skills-as-policy, ticks, issues, GitHub, git.

**Ten parameters:**

```
prompt          str          assembled above the seam
skill           str          harness-neutral; the adapter renders /name or $name
cwd             Path         the worktree
add_dirs        [Path]       the handoff directory
allowed_tools   [str]        optional, unset by default
permission_mode str
model           str | None
cap             Cap | None   {zone_tokens, stop_prompt, handoff_path}
timeout         float        mechanism here, policy in §6
sink            EventSink
```

**Two deliberate absences.** There is **no `session_id` / `resume` parameter** — sessions never
outlive an Action, so nothing durable stores one and no local cache can become load-bearing; the
seam mints one and returns it as telemetry only. And **`--setting-sources project` is a constant
inside the Claude Code adapter, not a parameter** — it is a Claude-Code-specific fix for a
Claude-Code-specific shadowing bug, so exposing it would leak one harness's detail through the
seam.

**Dispatch is by expansion, not by a model choosing to load a skill.**
([ADR 0006](../adr/0006-skills-are-dispatched-by-expansion.md)) Measured: the slash command *as
the prompt* loads the skill regardless of `disable-model-invocation`, while prose instruction
leaves the skill **not even listed** to the model when the flag is on — invisible rather than
refused, which is precisely how a real dispatch got improvisation instead of the skill. That is
why `skill` is a seam parameter rather than something the prompt assembler prepends: assembling it
above the seam would make the assembler emit Claude Code syntax.

**Five outcomes:**

| Outcome | Meaning |
| --- | --- |
| `Finished` | the agent completed its turn |
| `Capped` | stopped at the smart zone; a handoff was written |
| `Failed` | the agent ran and the work did not succeed |
| `TimedOut` | the orchestrator killed it on the wall clock |
| `HarnessError` | the harness itself broke |

⚠️ **`Capped` is a success shape, not a failure.** Getting that wrong makes every long dispatch
look like an error.

**`returncode` is read nowhere** — evidenced on both harnesses, since Codex exits `0` on a failed
task and Claude Code exits `0` on a blocked tool. All five outcomes derive from the event stream
plus the orchestrator's own knowledge of why it killed the process.

**Required alongside the outcome:** session id, final text, wall time, and `permission_denials` —
the only mechanical way to see a hobbled dispatch. Its *meaning* is now **invariant, not policy**:
it should always be empty, and a non-empty array means something is misconfigured. Emit loudly; do
not escalate.

**Capability-shaped, not required:** peak context, cost, turn count.

**The smart zone degrades to nothing** on a harness that cannot observe context mid-session. A
wall-clock cap is not a smart zone — it stops a dispatch at a moment with no relationship to
context rot. Such a harness is called with `cap=None` and its actions only ever terminate
`Finished`.

**The interface is expressed; the capability flags are not.** With one harness every flag is a
constant. The six recorded divergences survive as design constraints rather than as code with no
second branch — and the one that would silently *corrupt* behaviour, never reading `returncode`,
costs nothing and is already in.

#### Permission posture

**No per-role tool allowlist.** Role authority lives in the credential, where GitHub enforces it:
the reviewer holds Contents *read*, so a reviewer agent with completely unrestricted tools still
cannot push. The allowlist duplicated that boundary locally, silently, at exit `0`, and cost the
agent shell variables outright.

**Two risks accepted knowingly**, neither closable in v0.1: the role private keys are readable by
the dispatched agent, since it runs as the same OS user; and an unrestricted agent with network
access steered by issue text on a public repo is exactly the scenario §8's boundary does *not*
cover. Both are recorded rather than papered over. The Apps sit on two repos the owner controls
and revocation takes seconds.

#### The narration seam

**Two seams, not one.** The harness seam translates a harness's native stream into a small
vocabulary and stops there. The narration seam is a **sink** interface over orchestrator events,
of which translated harness events are one source among several. Fusing them means a future feed
could only ever render what an agent *said*, never what the *loop* did.

Eleven event types — six from the harness, five from `tick`:

```
SessionStarted   session_id, model, cwd
AgentMessage     text
ToolUse          name, one-line gist
ToolError        text
ContextSample    tokens
ActionFinished   outcome, wall, turns, denials, final_text

TickStarted      issue, tick number
StateDerived     state name, row number
MechanicalAct    what the orchestrator did itself
Waiting          why
Escalated        why
```

**Two sinks in v0.1.** The **terminal**, which renders everything, and the **pull request
conversation**, which subscribes to `ActionFinished` alone and posts its `final_text` as a comment
under the acting role's identity. **Rows emit; sinks decide.** Posting is not parsing, so the
trust boundary is untouched: the reviewer and judge read the report as context while the ladder
stays blind to it.

The terminal renders plain lines — no TUI, no progress bars, no cursor tricks, so output stays
readable when redirected. Context is shown per activity line against the smart zone:

```
● issue #17  tick 3
  ├ state  IMPLEMENTING  (row 10)
  ├ implementer  claude-sonnet-5
  │   ⟩ Read pyproject.toml                           26.1K/60K
  │   ⟩ Bash uv sync --locked                         31.4K/60K
  │   · Tests pass. Marking the PR ready for review.  39.5K/60K
  └ finished  116.3s · 25 turns · peak 39.5K
  ├ pushed my-team/17-scaffold-package
```

### 4. The skill payload and its installation

**Five skills, and the roster is closed:** `/mt-implement`, `/mt-create-pr`, `/mt-review`,
`/mt-judge`, `/mt-handoff`. Defined **as a closure** — what the ladder dispatches plus the
transitive closure of skills those name — so membership is enforced by a test rather than by a
list. Being *useful* is not the bar; being *named* is. `/code-review` and `/tdd` both fall out on
that rule.

**All five carry the `mt-` prefix.** ([ADR 0007](../adr/0007-payload-skill-names-are-prefixed.md))
Prefixed and unprefixed names are disjoint sets, so a personal `~/.claude/skills/implement/`
cannot shadow the payload's, and this repo's own `create-pr` — interactive, and reading a repo-local
doc, both forbidden below — coexists with the payload's without arbitration. ⚠️ The prefix reads
as weakening the by-hand promise and **secures** it: the promise is identical *behaviour*, and by
hand `/implement` could silently be somebody else's skill.

**Installed shape**
([ADR 0008](../adr/0008-the-payload-is-installed-into-the-target-repo.md)): real directories at
`.agents/skills/mt-<name>/`, relative symlinks at `.claude/skills/mt-<name>`, record at
`.my-team/skills-manifest.json`. `.agents/skills` is literally Codex's repo skill root and
`.claude/skills` is Claude Code's, which documents that its entries may be symlinks — one copy,
both harnesses, no translation layer. The dual root is insurance against a migration across repos
we do not control.

**Source shape:** the payload ships as **Python package data**, because the CLI is
`uv tool install`ed and `sync` cannot read a git clone. ⚠️ **Payload source looks exactly like a
skill and is not one** — nothing loads it, and editing it changes nothing until `sync` runs.

**The manifest is not a lock** — there is no upstream to pin against. It records, per skill,
**both** paths written (real dir and symlink, or it could never clean up), a content hash, an
`ejected` flag, and the version that wrote it.

**The six `sync` cases**, computed from what the package has, what the manifest says we wrote, and
what is on disk:

| on disk | in manifest | hash matches | `sync` |
| --- | --- | --- | --- |
| absent | — | — | **write** both paths, record |
| present | ✅ | ✅ | **overwrite** if the package differs, update record |
| present | ✅ ejected | — | **skip**, report |
| present | ✅ | ❌ | **refuse**, report — edited without ejecting |
| present | ❌ | — | **refuse**, report — foreign, never ours to touch |
| gone from package | ✅ | ✅ | **delete** both paths, drop record |

Two of those are decisions rather than table rows: **it deletes** a skill dropped from a future
payload — the safest possible delete, only a path we wrote and only while still byte-identical —
and **it never touches a file it did not write**, which is what makes the first run safe with no
manifest present.

The write set is `.agents/skills/mt-<name>/{SKILL.md,agents/openai.yaml}`, the
`.claude/skills/mt-<name>` symlink, and the manifest — **nothing else**. The installer writes no
docs into a target repo and never edits its `CLAUDE.md` or `AGENTS.md`.

**`sync` does not commit.** ⚠️ But refusing to commit exposes a failure mode: the worktree branches
off `origin/<default>`, so a payload synced and not pushed is present locally and **invisible to
every tick**, and an unrecognised slash command fails silently. Hence `doctor`'s
committed-on-the-default-branch check.

#### Nine rules binding all five skills

1. **The roster is the closure.** A payload skill may name `git`, `gh`, and the other four payload
   skills — nothing else.
2. **The prompt hands over only what the orchestrator alone knows.** The skill derives everything
   the repo can tell it.
3. **Self-contained.** No payload skill depends on a file it does not ship. A repo-local
   `docs/agents/*.md` is an **override** when present, never a prerequisite.
4. **Never ask.** No payload skill asks a question or waits for confirmation. Where the old text
   asked, it decides by a stated rule or proceeds and **flags the call in its report**. That is the
   honest reading of "identical by hand": the human loses a prompt they could have answered and
   gains a review point.
5. **Every skill specifies its final message, and never restates what it already wrote to the pull
   request.** The sink posts `final_text` after *every* Action, so an unspecified final message
   still gets posted — and left unstated, an agent narrates along the way and summarises none of it.
6. **No tool is ever named.** "Run the repo's checks", derived from CI config and `CONTEXT.md` —
   never a specific linter or test runner.
7. **The declaration goes last.** Push, re-verify, *then* mark ready. File the issues, *then*
   submit the verdict. Everything after a declaration is out of the declaring role's hands.
8. **Each skill states its definition of done as the fact its dispatching row's guard reads.**
9. **One argument: the issue number**, falling back to the `my-team/<issue>-<slug>` branch name.
   With neither, the skill states that and stops; stopping is not asking. The **briefing** follows
   the number in the same argument (§7). `/mt-handoff` is the exception — its argument is the
   destination path.

**Both invocation flags are flipped on all five** — `disable-model-invocation: false`, and
`allow_implicit_invocation: true` in the `agents/openai.yaml` sidecar. Dispatch no longer depends
on it, but `/mt-implement` invokes `/mt-create-pr` **by name**, and a flag there breaks composition
silently.

#### What each skill says

**`/mt-implement`** — definition of done stated as a **state, not an act**: *commit and push as you
go; if the pull request exists, ensure its title and body describe the whole change as it now
stands — invoking `/mt-create-pr` — then mark it ready.* Every round checks; only a round that
changes what the pull request is *about* rewrites anything, which is what stops a round-3 typo fix
from rewriting the body to be about the typo. At row 8 there is no pull request, so the round ends
at the push.

- **Precedence for reading the picture:** ⓵ **CI red beats everything** — rows 15 and 16 both guard
  on `ci_ok`, so a red tree can be neither reviewed nor judged; ⓶ then the judge's necessary-now
  points; ⓷ then the issue.
- ⚠️ **The reviewer's review is context, never instruction.** The reviewer is deliberately told not
  to rank or self-censor, so its list is *designed* to be noisy. An implementer that works it
  directly has bypassed the judge — the only actor allowed to say "that one isn't blocking." This
  is the single most important line in the skill.
- **Check the branch against its base and rebase if it conflicts.**
- **When it cannot finish:** commit and push what is safe, do **not** mark ready, say plainly why.
  One blunt sentence: **never mark ready to escape a problem.** The honest cost is that the loop
  burns rounds getting to escalation rather than exiting on the first refusal.
- **Four sentences of test discipline inlined** rather than by reference: where the repo has a test
  suite write the failing test first and then only enough code to pass it; test behaviour through
  public interfaces; one vertical slice at a time; expected values from an independent source of
  truth.
- **Final message:** deviations from the issue, judgment calls worth a reviewer's eye, and anything
  guessed at or blocked on.

**`/mt-create-pr`** — modify is the main path; create survives as a two-line fallback for a human
on a fresh branch. Branch creation and any rewind are the orchestrator's job and come out. ⚠️ **The
modify path must preserve the `Closes #<n>` footer** the mechanical creation wrote — the issue link
is invisible without a closing keyword, and verifying it is what catches a rewrite that dropped it.
Derive the base branch rather than assuming `main`. The commit standard goes **inline**, with a
three-step precedence: a repo-local `docs/agents/commit-conventions.md` wins; else, if recent
history on the default branch clearly follows another convention, follow the history and flag it in
the report; else the inline default.

**`/mt-review`** — the **whole diff, every round** (`origin/<default>...HEAD`). The question is "is
this pull request good", not "is this delta good". A **single review body with numbered points and
no inline comments** — numbering makes the judge's accounting mechanical to write and checkable by
a human reading the thread, where inline comments scatter the list and detach on rebase. **One
pass, not sub-agents** — the Action already has the smart zone for context, and a sub-agent's
reasoning is invisible to the narration seam. Reviews against, in order: the repo's own documented
standards, then the idiom of the surrounding code, then a short inline checklist as the floor.
**Contradicting an ADR is an explicit finding.** **Reads CI rather than re-running it** by default.
Final message: a short orientation note — how many points and where they concentrate, what it
deliberately did not examine, how confident it is.

**`/mt-judge`** — gives every reviewer point exactly one **disposal**: necessary now, worth keeping
(→ a new unlabelled issue filed under the judge's identity), or dropped. **It may block on a point
the reviewer never raised** — it is the last gate and `APPROVED` merges — **but holds only that one
bucket for its own findings**: a judge finding is blocking or it does not exist. **Two writes, and
the split is deliberate:** the `REQUEST_CHANGES` review carries *only* the blocking changes, and the
**disposal ledger** is the judge's `final_text`, which the sink posts. ⚠️ **The ledger names each
point, not just its number**, and **applies to `APPROVED` too** — without it, "dropped" is recorded
nowhere and the rule that makes the judge's filtering trustworthy is unfalsifiable. **Escalation by
judgment is the judge's own ritual** — swap the labels, comment with evidence, mention the product
owner — needing no new row, since row 1 already recognises `ready-for-human`. **File the issues
first, then submit the verdict**; escalation and a verdict are mutually exclusive. It is told
explicitly, because review-trained models hedge on all three: there are three disposals and no
fourth; what `APPROVED` does under the current flags (from the briefing, §7); and **a pull request
description gone stale against the diff is a "necessary now" change**, since that description is the
squashed commit message.

**`/mt-handoff`** — context-complete on its own, because the successor reads only the latest. It
names the **residue** as well as the prohibition: what was tried and rejected and why, what you were
about to do next, and what you know that the artifacts do not record. The anti-duplication rule
survives only *paired* with that residue — alone it excludes the diff for the implementer and the
whole pull request conversation for the other two, emptying their handoffs. Redaction stays.
Destination is the argument, never a baked-in path.

### 5. The agent roster

**Three roles. A role is an identity with authority, not a job.** Splitting **role** (identity,
provisioned once, ~6–8 minutes of browser clicking) from **Action** (one tick, one skill, free)
dissolves most of the roster question: pull-request authoring is a separate *action* under the
implementer's identity, not a separate agent.

| Role | App | `app_id` | bot user id | Contents | Pull requests | Issues |
| --- | --- | --- | --- | --- | --- | --- |
| implementer | `implementer-my-team` | 4652114 | 318751706 | write | write | read |
| reviewer | `reviewer-my-team` | 4608397 | 317436782 | **read** | write | read |
| judge | `judge-my-team` | 4652145 | 318752691 | write | write | **write** |

The reviewer is the only role denied Contents *write* — the write-side expression of "the reviewer
never pushes". The judge holds Contents *write* because the merge is a mechanical tick performed
with the judge's token: the orchestrator has no identity of its own. The judge holds Issues *write*
because it files the points it decides are worth keeping.

**Implementer** — receives the issue and the branch. Writes code, **verifies** with tests as it
goes (an observable), commits and pushes as it works, brings the pull request description up to
date, marks it ready. Never **reviews** its own work (a judgment), never approves, requests changes,
merges, or files issues.

**Reviewer** — receives the pull request. Reads whatever it deems necessary. Reports everything it
finds **without self-censoring or ranking**; the judge is the filter, and a self-filtering reviewer
drops findings by the one actor with a stake in its own list. ⚠️ This is a **starting position, not
a settled value** — if the noise proves expensive rather than merely untidy, dial it back. Posts a
`COMMENT` review. Never submits a formal verdict, writes code, merges, or files issues.

**Judge** — receives the pull request, the reviewer's review, the issue **and the code**. Disposes
of every reviewer point, and may block on what it sees itself. Submits `REQUEST_CHANGES` or
`APPROVED`. Never writes code, posts non-blocking suggestions, or performs the merge itself.

**Only the judge submits formal verdicts.** This keeps any read of review state a faithful readout
of the judge alone, and it is now **platform-backed**: a reviewer `COMMENT` leaves a protected pull
request `BLOCKED`, so the reviewer cannot unblock a merge even by accident.

**Read/write boundaries are prohibitions, not prescriptions.** The reviewer and judge may read
anything and run anything they judge useful; we do not instruct them *how* to reach a conclusion.
The boundary is a single prohibition: **neither ever writes code.**

**Merging is mechanical, not a role.** The judge's *decision* is the `APPROVED` review; the merge
is a tick. Nothing should re-litigate "should I merge" at the moment of merging, and
`--require-approval-to-merge` gates exactly that mechanical tick.

**No planning role in v0.1** — the planning segment is out of scope, which strips a project manager
of its actual job.

**Escalation splits by observability:** the orchestrator escalates on facts it can see (§6); the
judge escalates on judgment — underspecified, contradictory, unworkable — because no observation
produces that claim.

**Identity mechanics.** The orchestrator mints its own tokens (JWT → installation token, 1-hour
expiry) and passes them per subprocess; it **never** runs `gh auth switch`, which mutates global
state and races. Keys live at `~/.config/my-team/keys/<role>.pem`, mode `0600`, outside every repo.
**Config keys on the numeric `app_id` and `bot_user_id`, never on a slug** — measured, renaming a
live App preserves both its numeric identity and its installation.

⚠️ **Never let one role both open and approve the same pull request.** This is
platform-enforced rather than orchestrator-policed: an App approving its own pull request returns
`422 "Can not approve your own pull request"` with **no review recorded**, under protection and
without it. The implementer/judge split is what satisfies a required-approvals rule.

### 6. Failure, deadlock and escalation policy

**Non-convergence is one state, not seven.** Row 7 `NOT_CONVERGING`, whose guard is the disjunction
of four limits and whose action is to escalate. It sits below `OBSERVATION_UNSETTLED` because a
limit must never trip on an incoherent snapshot, and below `MERGED` because a merged pull request
converged however many rounds it took.

| Limit | Derived from | Default |
| --- | --- | --- |
| `max_revision_rounds` | judge `CHANGES_REQUESTED` reviews on the pull request | 3 |
| `max_ci_repair_rounds` | distinct head SHAs at which a required check failed | 3 |
| `max_rounds` | `convert_to_draft` timeline events | 8 |
| `max_stall_minutes` | elapsed since the last **progress event** | 90 |

**Countable off GitHub or it does not exist.** The two typed counters are strictly redundant against
`max_rounds`; they earn their place by making the escalation *message* specific, because "the judge
asked three times" and "CI failed three heads running" are different problems for a human.

**All four are counted from the most recent `labeled: ready-for-agent` event**, which is what makes
the swap-back a counter reset. ⚠️ **Counting and measuring cannot share that anchor:**
`max_stall_minutes` is floored at the start of the current `work` invocation, because counting
events since a label is indifferent to when the label was applied while *measuring* a duration from
it reads a weekend between triage and running as a stalled agent. That floor is the one piece of
orchestrator memory in the design — ephemeral, dead with the process, and a test input rather than a
hidden dependency.

**`max_stall_minutes` must exceed `max_action_minutes`**, or a single slow dispatch trips the stall
detector.

⚠️ **A progress event is an externally caused fact**: a new commit, a review submitted, a check run
completing. **The draft↔ready transition is excluded**, because the loop's own bookkeeping is not
progress — and counting it would let a judge/implementer livelock hold the stall detector open
forever at one full dispatch per lap. Prefer GitHub's own clock over git author dates, which are the
agent's clock.

⚠️ **Not counted, deliberately:** ticks, dispatches, and money.

**Escalation** ([ADR 0003](../adr/0003-escalation-swaps-the-labels.md)) removes `ready-for-agent`,
adds `ready-for-human`, posts one comment and exits. The comment carries its own evidence, because a
resumed loop re-derives everything and remembers nothing about why it stopped: which limit tripped
and its value, the evidence in one line, links to the specific artifacts, **the last Action's final
text** — where an agent says the thing worth reading — and the resume instruction spelled out.
Posted under the judge's identity, which is already the orchestrator's hand for mechanical acts.

**Resuming is the reverse swap, performed by the product owner**, and it is simultaneously the
re-authorization (§8) and the counter reset. Without that coupling the first escalation is
permanent: the human clears the label, re-runs, and the same limit trips on the first tick with the
same evidence.

**Human guidance is a prompt input, never a ladder input.** The product owner replies in the thread
the escalation landed in — the pull request conversation when one exists, the issue otherwise — and
the dispatched skills are instructed to read it, always rather than only after an escalation, so a
mid-run correction lands without stopping the loop. **The prompt reads prose; the ladder never
does.**

**Merge conflict** gets two rows, both **below** `IMPLEMENTING`, so nothing depends on what GitHub
reports for a draft. `CONFLICTED` converts to draft and the next tick dispatches the implementer; a
rebase is ordinary engineering work, the implementer has the worktree and Contents *write*, and the
other two roles have no business doing it. Escalating instead would hand the human the single most
common interference event. It needs no limit of its own — `max_rounds` counts its draft conversions
like any other.

**Process failure.** `max_action_minutes` **30** is a hang detector, not a budget — a real dispatch
was measured at ~116s. **No retry inside a tick:** `Failed` and `TimedOut` end the tick; the next
tick re-observes and, if nothing changed, re-dispatches, bounded by `max_stall_minutes` and
`max_rounds`. ⚠️ **`HarnessError` ends the whole `work` run, non-zero.** It is orchestrator
ill-health — a missing binary, a dead credential — not issue state, and looping on it burns for
nothing.

⚠️ **The load-bearing line: an outcome may shape pacing and run-termination, and may never become
State.** Outcomes are knowledge the tick acquires *after* deriving State, so feeding them back would
break the property that makes the ladder exhaustively testable. This is also why `Capped` needs no
handling at all.

**There is no budget ceiling, because nothing is left unbounded.** `max_rounds` bounds the laps,
`max_stall_minutes` a hang, `max_action_minutes` one dispatch, and `HarnessError` orchestrator
ill-health. A wall-clock ceiling on `work` would measure nothing the other four miss and would fire
mid-dispatch, the one moment you least want to stop. **The round limits *are* the budget, and that
is forced rather than chosen** — the only cost figure the harness reports is not spend. Money is
telemetry: rendered in the terminal, never read by the loop.

### 7. The briefing — what a dispatch actually carries

**The prompt is a briefing, not a payload.** ⚠️ **It carries only what the agent cannot look up.
Everything else it fetches itself.**

```
/mt-implement 17

Issue: 17
You are the implementer.
Roles on this repo:
  implementer  implementer-my-team[bot]  318751706
  reviewer     reviewer-my-team[bot]     317436782
  judge        judge-my-team[bot]        318752691
Required checks: lint, types, tests
A previous session left notes for you in ~/.local/state/my-team/mcnewcp-personal-assistant/17/handoffs/
```

Every line survives a *"could the agent get this?"* test: the issue number is the argument; the
role line says which identity is *yours*, so the agent can find its own prior work; the roles block
is config, carrying logins **and** numeric ids because the two API surfaces disagree on the `[bot]`
suffix; the required checks are config, and load-bearing, since rule 6 forbids a skill naming a tool
and this is the only thing that makes "run the repo's checks" concrete; the handoff directory is a
local path GitHub has never heard of.

| Action | Shape |
| --- | --- |
| `UNSTARTED` → `/mt-implement` | The same document — three lines, because there is no pull request and no handoff yet. The difference falls out of the Observation, not out of a second template. |
| `IMPLEMENTING` → `/mt-implement` | As above. |
| `NEEDS_REVIEW` → `/mt-review` | Same, handoff line when one exists. |
| `NEEDS_JUDGMENT` → `/mt-judge` | Drops **Required checks** — both guarding rows require `ci_ok` — and gains the merge-consequence line. |
| the `/mt-handoff` tail | **`/mt-handoff <path>` and nothing else.** The session is hot and holds everything by construction. |

**The one line the judge gets that nobody else does:** *your approval merges this pull request
immediately*, or *your approval releases it for a human's approval before merge*. It is not a gauge
— it is the semantics of the judge's own declaration, and `--require-approval-to-merge` is a flag no
agent can observe. With the flag set, the sentence the skill would otherwise state is simply false.

⚠️ **The briefing tells an agent nothing about its budget.** No counter, no limit, no State name, no
row number, no tick number, no previous outcome. **Every limit tripping produces an escalation,
which is safe; knowing how close the limit is pushes an agent toward the unsafe act to avoid it** —
the implementer toward marking ready to escape a problem, the judge toward the one irreversible act
in the system. It fails the same test that keeps the State name out: *what does the agent do
differently?* Here, the wrong thing. The design principle survives without the number: the judge is
told its own additions cost a full revision round — a cost statement, not a live gauge.

**Not carried, and looked up instead:** the issue body, the diff, the pull request, the reviews, the
disposal ledgers, the thread, CI status, CI logs, the base branch, the code.

**Both trust paths live in the skills, not in the assembler.** Trusted humans by `authorAssociation`
— free on every comment payload the agent already fetches — and roles by the numeric ids the
briefing supplies. ⚠️ **Filtering the prompt was never containment**: the agent reads the whole
untrusted thread the moment it fetches the pull request, so a curated transcript bought nothing at
the cost of a second implementation of the trust predicate. The hole an earlier ticket found stays
closed, because that hole was that *nothing made anyone look* — and a skill instruction makes them
look.

**Ordering and truncation dissolve.** Nothing in the briefing grows — not with the diff, not with
the length of the thread, not with the number of rounds.

⚠️ **The briefing may safely read fields the ladder must not trust.** A wrong briefing costs a
wasted paragraph; a wrong State costs a wrong action.

**The handoff is pointed at, not inlined.** Reading it becomes the skill's job, so each of
`/mt-implement`, `/mt-review` and `/mt-judge` gains a **read-only** line paired with the sentence
that neutralises the obvious risk: **never write a handoff unless told to.**

### 8. The trust boundary

**The label act is the authorization, not the authorship.**
([ADR 0005](../adr/0005-the-label-act-is-the-authorization.md)) An issue enters the loop when a
**trusted human** applies `ready-for-agent` **and** the body carries no edit by an untrusted editor
since that label event. GitHub *enforces* that only triage-or-above can apply a label, so the label
already proves someone with write access read the issue and vouched for it.

**Author-gating was rejected** — it forbids the case the motivating incident obscures, where an
outsider files a genuinely excellent issue and the maintainer wants it worked, and its only remedy
discards the reporter's attribution to satisfy a check the maintainer already performed by hand.
**The conjunction was rejected too**: the labeller's act already asserts everything an author check
would establish.

**Trust is derived, not configured:** `authorAssociation ∈ {OWNER, MEMBER, COLLABORATOR}`. The
`permission` API is the exact primitive that approximates, and it is used **once, in `doctor`**, on
`product_owner`. ⚠️ One documented widening: GitHub reports `COLLABORATOR` for any invited
collaborator, including read-only.

⚠️ **Measured: every App reads `author_association: NONE`**, including one installed with write
permissions. `authorAssociation` is a **collaborator-list readout, not a permission readout**. Two
consequences, and the second is the better guarantee: it can never be the trust primitive for a
non-human actor, so role identities keep the numeric-id mechanism and the human predicate never
touches them; and the roles fail the human-approval predicate **structurally** rather than by
absence from a list.

**Only a `User` can authorize.** A `ready-for-agent` applied by any App does not authorize.

**Comments need no freshness clause, unlike the issue body** — GitHub restricts comment editing to
the author and users with write access, so every possible editor of a *trusted* comment is itself
trusted. The issue body is the exception only because its author can edit it forever regardless of
association.

**On failure, escalate — because the escalation *is* the un-authorization.** Silent halt was the
conservative candidate and was rejected because the provoked write is **self-limiting**: once
escalated, row 1 catches every subsequent tick, so it is one write per re-authorization rather than
a loop. The "halt, the human is already here" rule does not apply — in the tampering case the human
is not here, the tamperer is.

⚠️ **On a public repo anyone may submit a formal review**, so an unrecognised-identity guard written
when only three identities were in view would let any passerby park the loop. Untrusted reviews now
leave the Observation at **parse**, and row 4's guard narrows to a **`Bot`** review from an App id
not in config, which is genuinely ambiguous. The role predicate and the human predicate together
partition every review author into role / trusted human / untrusted, and only the first two are
evidence.

⚠️ **This is authorization, not injection defence** — stated because it is the part most likely to
be misread later. The real containment is structural and was decided elsewhere: no prose is parsed
anywhere in the state machine, role authority lives in the credential, and GitHub itself refuses a
self-approval. **Injected prose can steer what an agent writes; it cannot move the ladder.**

### 9. The workspace

([ADR 0001](../adr/0001-isolated-worktree-and-handoffs-outside-git.md))

```
~/.local/state/my-team/<owner>-<repo>/<issue>/
├── worktree/          # the git worktree, and nothing else in here
└── handoffs/
    ├── implementer-01.md
    └── reviewer-01.md
```

**A `git worktree` per issue, justified by autonomy rather than parallelism.** Working in place
would lock the human out of their own repo for the length of an unattended run — a contradiction in
a tool whose premise is "go do this while I do something else." Parallelism is a free consequence.
Placing it outside every repo means there is nothing to `.gitignore`; keying by `<owner>-<repo>`
stops a second target repo colliding on issue numbers. Disk cost is negligible, measured: ten
identical `uv` virtualenvs are 2 MB of actual free-space delta against 26 MB logical.

**Branches are `my-team/<issue>-<slug>`, created mechanically by the orchestrator** off
`origin/<default>` after a fetch, never from a local ref. `<type>` is dropped as the one segment the
orchestrator cannot derive reliably. **Discovery** is the `my-team/<issue>-*` glob before a pull
request exists and `headRefName` after — and ⚠️ `closedByPullRequestsReferences` is **empty unless a
closing keyword is used**, which makes it the *verification* that a pull request linked its issue,
never the lookup.

**The human's working tree is dissolved, not answered.** `my-team` never reads it and never reads
local branches. There is no dirty-tree policy, no stash, no refuse-to-run.

**Handoffs are local-only and never in git**, named by **function** (not persona), namespaced per
function because two roles can hand off on the same issue, and **accumulating** rather than consumed
on read, so a role that dies before writing its own handoff has not destroyed the only document.
⚠️ **They must sit *beside* the worktree, not at its root** — verified, a file at the worktree root
is untracked in that working tree and `git add -A` stages it. The orchestrator grants the write with
`--add-dir`.

Taking handoffs out of git deletes three problems at once: the scrub commit, the merged-tree-differs-
from-approved-tree conflict with dismiss-stale-reviews, and the stray-file merge precondition.

⚠️ **The workspace is acted on, never observed.** Making local git a co-equal observation source was
taken seriously and rejected because **no action changes** — State is the value that names one
action, so a distinction the ladder cannot act on differently is not a state. The one case that
mattered, committed-but-not-pushed, is dissolved by the sweep push. The bar for reopening is a single
question: *which action changes?*

**The push is the skill's and the orchestrator's, and neither is trusted.** `/mt-implement` commits
and pushes as it works — so a human running it by hand gets the same result and a crash mid-round
leaves work on origin — and the orchestrator sweeps with `git push -u origin <branch>` as the tail of
every implementation dispatch, a no-op when the agent already pushed or committed nothing. This is an
**Action**, not a second Observation.

**Teardown is a state transition, not a `finally` block.** Merged → remove the worktree (auto-delete
takes the branch). Abandoned → an explicit `my-team clean`. **Crashed → the directory is deliberately
left in place; it is the resume substrate.** A pre-existing directory for an issue *is* the resume
path: reuse it, never recreate.

### 10. Continuity — the smart zone and the handoff

**The trigger is context *rot*, not context *exhaustion*.** Measured: a ~24.4K floor (system prompt
+ skills + project docs, paid before a single useful token) and a 44.3K peak on a complete real
issue, against an auto-compact threshold of 934K. Calibrated against that ceiling the handoff would
be near-dead code; calibrated against the **smart zone** — the span within which a model still works
well — it fires on every long dispatch.

**Context is read passively and free.** Every `assistant` message's `usage`
(`input_tokens + cache_creation + cache_read`) **is** the context size, deduped on `message.id`. The
orchestrator already consumes that stream, so **no control channel is needed** — and none is used for
the stop either: **SIGTERM, then resume carrying the stop prompt**. The entire mechanism is
control-channel-free. Usage arrives per assistant message, so **overshoot past the zone is bounded by
one turn**, and the handoff write does not need to happen below the zone — only after it, since
writing a handoff is a shallow task. There is no reserve mechanism and none is needed.

⚠️ **The write and the successor use opposite session policies, and this is the easy mistake:**

| Beat | Session |
| --- | --- |
| Write the handoff | **resume** the capped session — hot context is the whole point |
| Successor picks up | **a brand-new session** — *never* resume, which would reload the rot and defeat the mechanism |

**It is the tail of a tick, not a tick.** No new Observation, so an Action terminates either
*finished* or *capped*.

**One format, all three roles** — rot degrades review and judgment as much as implementation, and the
residue is the same for all three. **Latest only**; the successor reads one document, because tokens
are not the binding constraint at these sizes and **comprehension** is: three overlapping partial
narratives make a successor work out which is still true.

**Skill owns content; the prompt owns destination** — `<state>/handoffs/<function>-NN.md`, computed
by the orchestrator, because the agent should not be listing a directory outside its worktree to pick
a filename. The stop prompt is orchestrator-owned.

**A missing handoff is never an error and is never retried.** Present → the skill reads it; absent →
dispatch without it. Retrying the write is the one behaviour that would turn a degradation into a
hang.

**No circuit breaker on handoff count.** Counting files on disk would make a local directory
load-bearing for an orchestrator decision, which the State rule forbids. The elapsed-time stall
detector already covers grinding without knowing handoffs exist.

## Testing Decisions

**What makes a good test here:** it asserts on externally observable behaviour — the State a snapshot
derives, the Action selected, the calls a port received — never on an implementation detail and never
on anything a model wrote.

### The three fakes, and where each goes

Fakes go **at the port**, not at the wire and not at the subprocess, so a fake speaks the design's own
vocabulary — `Observation`, not JSON. ⚠️ **The honest cost: a port fake never exercises `gh` argument
construction or a single JSON-shape assumption** — which is exactly where every landmine so far was
found. The two decisions below exist to cover that, not to pretend it away.

- **The GitHub port** gets **two** fakes, deliberately
  ([ADR 0004](../adr/0004-two-fidelity-github-fakes.md)): a **builder** producing `Observation` values
  directly for the row tests, since several rows are only reachable as nonsense; and a **stateful
  world** used only by the convergence tests.
- **The harness port** gets a fake whose actions perform their *real* definition of done.
- **The local-git port** is write-only, so its fake need only record calls.

### `observe()` splits into fetch and parse

`fetch(repo, issue) -> RawSnapshot` (all I/O, no logic) and `parse(raw, config) -> Observation`
(pure). **`parse` is the only seam at which a real captured payload can enter a test.** Fixtures are
**captured by script, never hand-written** — hand-written JSON is the design's assumptions wearing a
costume.

### The ladder is data

Three obligations, and the third forces the design consequence:

1. **One case per row** — nineteen — asserting the State name **and** the selected Action.
2. **A shadowing case per ordered pair the order exists to break.** Not all 171 pairs: only the ones
   the record names — the draft-vs-finished tie; `MERGEABILITY_UNSETTLED` and `CONFLICTED` sitting
   below `IMPLEMENTING`; `NOT_CONVERGING` below both `OBSERVATION_UNSETTLED` and `MERGED`;
   `UNAUTHORIZED` above `AMBIGUOUS`.
3. **A meta-test that fails when a row has no case.**

⚠️ **(3) is unwritable against an `if`/`elif` chain**, which cannot be asked how many rows it has —
which is why the ladder is a list of `(name, guard, action)`.

### The convergence property — the load-bearing test

> **No tick may derive the same state as the previous tick unless the world changed.**

That is the guard invariant expressed as runtime behaviour instead of a table checked by hand, and it
is **the only thing that would have caught the livelock a real run found** — where every generic
safety net missed it, because each tick succeeded: no error, exit `0`, no denials, the action
completing correctly every time.

Adversarial worlds alongside the happy path: a harness that does nothing (must escalate on
`max_stall_minutes`, not spin); a judge that always requests changes; CI always red; and the specific
judge/implementer lap — commit nothing, mark ready — which must trip the clock, because the
draft↔ready transition was struck from the progress-event set precisely so it would.

### How purity is enforced rather than intended

- **The signature.** `derive(observation, now, work_started_at)` takes no client, so it **cannot** do
  I/O. The strongest of the three and it costs nothing.
- **An import contract in CI** — the ladder module may not import `subprocess`, an HTTP client, or the
  GitHub and harness modules. This catches the future commit that "just needs to check one more thing".
- **The clock is a parameter, never read inside** — which is also what makes `max_stall_minutes`
  testable in microseconds rather than in ninety minutes.

### The contract test, and why it is mandatory

⚠️ **The standing risk is that two fakes disagree, and that the builder mints observations the real
world never produces.** This is not hypothetical: every load-bearing fact in the state machine was a
*surprise* when measured. **The contract test is the only thing tying the builder to reality** — it
drives the ports directly to construct each observable configuration, captures the raw JSON, and
asserts `parse` yields what the builder claims. It **runs under the role App tokens, not a personal
token**, because half the facts it protects only exist for App identities. Manual and nightly;
**never on a pull request**. Deleting it as redundant is the failure mode, which is why the ADR says
so in writing.

### The fixture repo

**`mcnewcp/my-team-fixtures`** — public, matching both real repos, because on a private repo some
protection features are plan-gated. Two zones: **a permanent small-but-real Python package with real
CI**, so that "add a `--verbose` flag" is genuine work, and disposable generated branches, pull
requests and issues. ⚠️ **CI states need a workflow that can be *steered*** — three rows cannot be
constructed without real check runs, so the repo ships a workflow reading a committed
`.fixture/ci-verdict` and passing, failing or sleeping accordingly.

⚠️ **Rebuild is not fully scriptable, and that is accepted.** Measured: `gh`'s own token is refused by
the installations API, so **installing the three Apps is three UI visits per rebuild**. Everything
else scripts cleanly. ⚠️ **Setting the installations to "All repositories" is the obvious fix and is
rejected** — it converts the bounded key-readability risk §3 accepted into an unbounded one, to save
three clicks on a rare operation.

### The acceptance run and the release rehearsal

Two things, needing two names — and `smoke test` was already taken by a narrow live-API capability
probe.

- **The acceptance run** — once, in `mcnewcp/personal-assistant`, on a **genuine** issue that was
  wanted anyway. This **is** the acceptance criterion rather than a proxy for it: a fixture-repo
  version would prove the loop turns over but could not prove the implementer copes with a real
  codebase, real CI and real project docs, which is the part that would actually surprise us. And on
  a genuine issue it is not litter — it is the first pull request the team shipped.
- **The release rehearsal** — recurring, in the fixture repo, gating each release, growing into a
  scenario library of issue-plus-expected-terminal-outcome. v0.1 ships exactly one entry (merge, exit
  0); escalation scenarios are the natural second.

Neither runs in CI. There is no attempt at determinism, because determinism here would mean asserting
on what a model wrote. The output is a verdict and a wall time.

### CI gates for the orchestrator repo

Ruff (lint + format check), mypy `--strict`, pytest — with a **split coverage floor rather than one
number**: **100% on the pure core** (the ladder, `derive`, `parse`, `assemble`), because they are pure
functions over plain data and anything less is an admission that a row or a branch is unreached; ~85%
globally as a ratchet that only moves up. A single number averages the untestable adapters against the
core and hides exactly the gap that matters.

These double as this repo's own `required_checks` when the team is pointed at its own source, since
the gate is declared and never inferred.

**Built test-first for the pure core**, not dogmatically for the adapters. ⚠️ A useful forcing
function: **if a row's expected `Observation` cannot be written down, the row is not specified yet.**

Plus one cheap test earned by the prefix: **every skill referenced by another skill exists in the
payload.** **Wide reading** — any `/token` in a payload `SKILL.md` that is not a payload member fails,
since the narrow reading would pass a skill still naming a dropped one. **Allowed set computed from
the payload tree**, not a hardcoded five, so a shared sub-skill joins by being present and prefixed.
It reads the package-data source, so it runs in CI with no target repo present — and it runs over the
**authoring tree too**.

### Never tested, deliberately

**Nothing an agent wrote is ever asserted on** — code quality, review quality, judgment quality, skill
prose. **No LLM-as-judge anywhere in the suite.** Worth stating because the temptation is concrete.
Also excluded: the harness's own CLI behaviour (re-measured by hand when the binary moves, not pinned
by a test that would fail for the wrong reason), the terminal renderer's exact layout, and every
telemetry value including `total_cost_usd`, which is not even money.

⚠️ **But the line sits one step out from "don't test agents": the prompt assembler is tested; the
prompt's effect is not.** `assemble` is a pure function returning a handful of lines and is fully
assertable — and that is exactly where a real hole was found, where a product owner could write a
paragraph of guidance and the next implementer would never see it. **That hole was a missing input,
not a bad agent.**

### Dogfooding

One hazard dissolves on inspection: the running orchestrator is the **installed** package while the
agent works in a worktree, so an implementer editing the ladder cannot affect the loop currently
executing it.

Three preconditions: the install-into-self shape is settled (it is, §4); the acceptance run has passed
in `personal-assistant` **enough times to have a felt failure rate**; and this repo has real CI
declared in `required_checks`.

⚠️ **A fourth hazard is real and gets no machinery: the self-modifying payload.** An implementer
editing the payload in a worktree, merged, means the *next* dispatch runs skills an agent wrote — the
one loop in the design with no human in it. It is handled by **habit, not by a feature**: the loop only
works issues a human labelled `ready-for-agent`, so the human does not label the ones touching the
ladder, the ports, or the payload. The authorization label already *is* the control, and a
protected-paths feature would be a second, weaker copy of a boundary that already exists.
`--require-approval-to-merge` on for the first dogfood runs.

---

## Out of Scope

Each of these was considered and ruled out **for v0.1 specifically**. They return as fresh efforts,
not as resumptions.

- **Multi-issue autonomy** — `my-team run` picking up issues continuously, and how it orders them.
  v0.1 is deliberately one issue, which is also why `ready-for-agent` is authorization rather than a
  lock and why there is no selection step to pre-filter.
- **A triage/planner role** — an agent that works *unlabelled* issues, adds context, and rules on
  whether each is ready. Wanted, and the natural consumer of the issues the judge files, but it only
  has a job once the loop picks its own work. ⚠️ It inherits a requirement: **no App is a trusted
  human**, so a planner-applied label does not authorize. Admitting one makes trust **transitive** —
  the planner's authority comes from whoever authored the spec it read — and *that* boundary, not the
  App id, is the work. No `trusted_apps` key ships in v0.1, deliberately.
- **Parallel agents.** The door is open and deliberately unused: the worktree-per-issue shape is what
  parallelism needs and was adopted for autonomy reasons that stand on their own.
- **Codex as a working second harness.** The *seam* is in scope and is designed against Codex's real
  shape — six recorded divergences, `AGENTS.md` rather than `CLAUDE.md`, `$name` rather than `/name`,
  the dual skill root. A second implementation is not.
- **Personas.** Named characters and the persona-pack mechanism that would let a "professional" pack
  replace them for work deployments. v0.1 ships the working loop; personality is a later version's
  concern. Narration survives keyed by **role**; only the name and voice go. **Nothing in this
  document carries a persona name**, and the Apps are role-named.
- **Chat-surface narration** — Slack or Obsidian as the narration home. The pull request conversation
  already is the thread for review discussion, and a chat surface arrives later as a **third sink**
  rather than a redesign.
- **Visualization** — board view, human inbox, an animated view of the team at work. The only
  constraint this places on v0.1 is already met: a view can render only what the loop emitted, which
  is why narration is an event vocabulary rather than print statements.
- **Rate-limit-aware pacing** — watching usage limits and slowing as they approach. Cheap to add later
  because pacing lives in one place; the round limits and stall detector bound the loop instead.
- **Prompt-injection defence beyond the tracker** — CI logs, dependency READMEs, `.md` files on a
  contributor's branch, and whatever a research skill fetches from the open web. §8 draws an
  *authorization* boundary and explicitly disclaims this one rather than letting it be assumed. ⚠️ The
  accepted risk that **role keys are readable by the dispatched agent** stands unmitigated and is
  recorded as such.
- **Planning-segment automation** — a planning agent running spec and issue-breakdown skills. Already
  well served by running them by hand, and it is the part where the human *wants* to be in the loop.
- **Stewardship-segment automation** — scheduled codebase-improvement reviews feeding proposals back
  into the loop.
- **A tool sandbox.** Only a separate OS user or a container closes the key-readability risk, and both
  are real sandboxing.

## Further Notes

### Gaps this assembly closed

Six things no ticket decided, filled here rather than smuggled. Each is cheap to reverse.

1. **Exit code `4` for `HALTED`.** Four codes were named — merged, error, escalated, awaiting
   approval — and `HALTED` fits none: it is neither an error nor a request for attention. Folding it
   into `0` would tell a wrapper that a closed issue merged.
2. **The exit-vs-poll rule generalised.** The record named rows 1, 2, 7 and 18 as exiting and omitted
   `UNAUTHORIZED` and `AMBIGUOUS`, which also escalate. Stated as a rule instead: **every row whose
   action is escalate exits**; `MERGED` exits `0`; `NEEDS_HUMAN_APPROVAL` exits `3`; the machine polls
   only on rows that resolve on their own.
3. **`--once` rather than a separate `tick` command.** `tick` is the primitive and is genuinely useful
   to step by hand, but a second command doing nearly the same thing is surface for nothing.
4. **`--require-approval-to-merge` is a flag with a config default.** The record treats it as a flag in
   one place and as config content in another; a flag that overrides an optional
   `require_approval_to_merge` key satisfies both.
5. **The full `doctor` check list**, assembled from six tickets that each contributed one or two
   checks, split into blocking and advisory.
6. **`init`'s exact write set and `work`'s flag set**, assembled the same way.
7. ⚠️ **`init` creates the two triage labels; `doctor` checks they exist.** Found by assembling
   rather than by reasoning: `ready-for-agent` and `ready-for-human` are named throughout the design
   and **do not exist as labels on this repo today**. They are the tool's own vocabulary rather than
   the repo's policy, and without them nothing can be authorized, so creating them is a fair thing
   for `init` to do — unlike merge policy or branch protection, which it must never touch.

One check was **dropped**: the warning that a personal skill shadows a payload skill. The `mt-` prefix
makes the name sets disjoint, so the hazard no longer exists.

### Measurements still outstanding

Each is a fact the design currently reasons about rather than knows. None blocks implementation; all
are one experiment each, and the honest thing is that they are listed.

| Measurement | Why it matters |
| --- | --- |
| Does GitHub compute `mergeable` for **draft** pull requests at all? | When it is `null` on a draft, neither the orchestrator nor the agent knows there is a conflict, and `max_rounds` carries it to escalation. |
| Does a slash command **mid-prompt** still expand? | Decides whether a briefing could ever name a skill in its body. Only the command-as-whole-prompt case was measured, which is why the stop prompt is `/mt-handoff <path>` rather than a sentence. |
| The exact `permission_mode` value on the current binary. | Six modes exist on the CLI and are not documented in it. |
| Does the `rm` path-confinement guard survive a permission bypass? | Expected to disappear, but that is a guess; the seam currently leans on it. |
| `require_last_push_approval` under protection. | Expected safe — the judge approves after the implementer's last push and they are different actors — but that is reasoning, not measurement. |
| Are pending **review requests** dropped on draft conversion? | Documented, unexercised. It is the one path where the latch is known to be destructive. **Nothing in this design may come to depend on review requests as signal.** |
| Does Codex follow symlinks under `.agents/skills/`? | The dual-root recommendation is deliberately built not to depend on it. |

### Possible sharpenings, recorded not adopted

- **`git ls-remote origin` as row 5's guard.** It reads the ref straight from GitHub with no REST
  caching — still GitHub as the source of truth, just a different transport. Row 5 works, and a real
  run found the lag window narrower than feared (19 seconds after a push it already read settled), so
  this is a sharpening rather than a defect.
- **The reviewer's no-self-censoring instruction.** A starting position, not a settled value. Revisit
  if the noise proves expensive rather than merely untidy.

### Every measured fact was a surprise

Worth naming as a working assumption for whoever builds this. `reviewDecision` reading `null` with a
fresh `APPROVED` in the list; REST and `gh` disagreeing on the `[bot]` suffix; `head.sha` lagging a
push by ~10s; timeline timestamps colliding at second resolution; `mergeStateStatus: CLEAN` on a
draft; an App reporting `author_association: NONE` while holding write; `total_cost_usd` being list
price rather than spend; a blocked tool exiting `0` in five distinct denial shapes; the context floor
sitting at 24.4K before a single useful token.

None of these was predicted. **Measure before depending on a platform behaviour**, and prefer the
primitive to the computed summary every time.

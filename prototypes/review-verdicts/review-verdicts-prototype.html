The two causal findings


      
1 · A Reviewer App blocks only when it holds Contents: write

      

        The same App, submitting the same verdict against the same protection, is inert with
        contents: read and a hard blocker with contents: write.
        authorAssociation stayed NONE in both cases, so that
        field cannot be used to predict whether a verdict will bite.

2 · A review's weight is evaluated live, not frozen at submission

      

        Review 5090488756 — one APPROVED from the Judge, submitted once
        at 13:48:57Z and never resubmitted — was toggled between counting and not counting purely
        by changing the Judge App's permissions underneath it. An A→B→A reversal on a single
        unchanged artifact:

        Operational consequence
        Narrowing or widening an App's repository permissions silently changes the mergeability of
        pull requests that are already open, with no event on the pull request and no change to any
        review artifact. Permission changes are retroactive across the whole open queue.
      

    


    

      
Dismissal authority

      

        

          
AttemptJudge grant / policyResponse

              metadata:read + pull_requests:write, no admin, no dismissal policy
              200 — dismissed
            

            

              Add Judge App to dismissal_restrictions.apps
              Repo admin (user token)
              422 Only organization repositories can have users and team restrictions
            

            

              Re-dismiss an already-dismissed review
              Judge installation token
              422 Can not dismiss a dismissed pull request review — an artifact-state error, not a permission signal
            

          
        

      

      

        Least permission established
        Pull requests: write plus mandatory Metadata: read is sufficient
        for the Judge to dismiss a blocking Reviewer verdict. No administration grant, no repository
        admin role, and no dismissal_restrictions entry is required — which matters,
        because that policy lever does not exist on a user-owned repository at all.
      

    


    

      
A later push does not clear a verdict

      

        With dismiss_stale_reviews: true and count=0, the implementer
        pushed a second commit (ee21028) over a live blocking verdict. The review was
        not dismissed:
      

      
protection  { "required_approving_review_count": 0, "dismiss_stale_reviews": true }
push        PUT /contents/prototype-104.md -> 200  (ee21028adecd79c343fcad2856e97e5c3d04868f)

            5090488756  APPROVED           judge-my-team[bot]

reviewDecision    CHANGES_REQUESTED
mergeStateStatus  BLOCKED

      

        Read carefully
        dismiss_stale_reviews stales approvals. It does not stale a
        CHANGES_REQUESTED. A Remediator's commit therefore cannot self-heal a blocking
        verdict — only an explicit dismissal, or a fresh approving review from the same Principal,
        will clear it.
      

    


    

      
Verdict

      
    
        
  1. 
          Yes — Reviewer → Judge → Integrator can leave a platform blocker. A
          Reviewer App holding Contents: write produces a CHANGES_REQUESTED
          that blocks at every required-approval count tested, and survives later commits even with
          stale dismissal enabled.
        
    2. 
        
  2. 
          But the Judge can always clear it. Dismissal succeeded with nothing but
          Pull requests: write. There is no configuration in which the block is
          reachable and the remedy is not.
        
    3. 
        
  3. 
          Whether the block exists at all is a permissions choice, not a protection
          setting. Grant the Reviewer Contents: read and its verdict is
          advisory — the platform ignores it entirely and the orchestrator must enforce it. Grant
          Contents: write and the platform enforces it for you.
        
    4. 
        
  4. 
          dismissal_restrictions is unavailable on user-owned target
          repositories, so it cannot appear in any design that must work outside an organization.
        
    5. 
        
  5. 
          Review weight is live-evaluated against the reviewing Principal's current
          permissions, making permission edits retroactive across all open pull requests.

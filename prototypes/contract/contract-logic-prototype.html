Make the definition of done feel frozen.

This click-through asks whether one GitHub issue comment can be pleasant for a Product Owner to read, strict enough for a machine to parse, and safely recoverable after retries, corrections, or tampering.

The question this prototype answers

Does an append-only, digest-bound Contract protocol give the Contractor, Product Owner, Implementer, Auditor, and Integrator one unambiguous definition of done without turning the GitHub conversation into a wall of serialization?

  • Readable Markdown is generated from RFC 8785-canonical JSON in the same comment.
  • A Product Owner approves the exact comment with a thumbs-up reaction.
  • Corrections are new revisions; an edit is tampering, never a correction.
  • The pull request repeats the comment permalink and digest.

Rules under test
One authority, two renderings

The JSON object is normative. The Markdown is generated from it and reparsed before posting.

The digest has one representation

Lowercase SHA-256 covers the UTF-8 RFC 8785 form of the JSON object, excluding the digest itself.

Criterion IDs never drift

AC-001 may survive a revision only when its whole object is unchanged. Changed meaning gets the next unused ID.

Approval binds the comment

With the v0.1 gate on, only the configured Product Owner's 👍 on the exact, unedited comment activates it.

Clarification protects product choices

If an outcome, proof oracle, budget, or path boundary requires choosing user-visible behavior, the Contractor asks; approval is not permission to guess.

Verifiability has two owners

Preflight proves every criterion has deterministic proof structure. Contractor judgment plus Product Owner approval establish that the oracle actually proves the outcome.

No edits, even harmless ones

Any edit timestamp invalidates that Contract and escalates. A correction is an append-only successor.

A pending successor blocks

An approved revision remains historical, but a later candidate pauses implementation until that candidate is approved.

Implementation closes the chain

Once work starts, issue-body edits escalate instead of expanding scope, and new Contract revisions are rejected.

Free play

Push events in any order. Rejections are part of the prototype.

Exact field semantics

FieldMechanical meaning
sourceThe issue URL and body digest the Contractor read. It must still match when approved.
digestLowercase SHA-256 over UTF-8 RFC 8785 canonical JSON; carried outside the object so it never hashes itself.
acceptance_criteriaNormative, falsifiable outcomes. IDs are issue-local and never reused; preflight can validate their proof links, not their semantics.
test_planAt least one deterministic proof plan covers every active criterion.
non_goalsSalient exclusions, not acceptance checks and not an exhaustive list of all absent features.
test_budgetA hard cap on new leaf cases discovered at PR head but absent at the base SHA. Every case traces to an AC or demonstrated blocking defect; exhaustion escalates.
scope_pathsAn allowlist over changed Git paths; both sides of a rename must match. Reading remains unrestricted.
supersedesThe exact prior comment permalink, revision, and digest; null only for revision 1.

What your reaction should settle

The prototype has opinions on purpose. These are the pressure points worth disagreeing with.

Does 👍 feel like approval?

It binds directly to one comment and one actor, but it is less ceremonious than a formal approval comment.

Is the comment readable enough?

The Product Owner sees outcomes first; serialization is collapsed. Is any section still too implementation-shaped?

Is the hard boundary believable?

After implementation starts, every scope correction escalates or becomes follow-up work; nothing silently recontracts.

Prototype — throwaway

A Ledger that remembers judgment without inviting endless review

This single-file demo exercises a proposed finding and Ledger model for a realistic two-round pull request. Press the guided steps or attack the protocol in free play; the full GitHub-derived state, readable comment, and normative JSON update after every act.

The question

Can one mutable PR conversation comment make subjective review bounded, persistent, readable, and mechanically recoverable — including exact retries, stale reviews, forbidden re-raises, interrupted Judge writes, and two concurrent Judges?

The specimen uses acme/payments#418: round one finds three realistic defects, the Judge blocks one, files one, and drops one; remediation changes the head; round two must account for the blocker and may inspect only that delta.

  • Identity has two faces. RFC-8785 + SHA-256 over a stable identity object is authoritative; F-001 is only its never-reused display label.
  • Old blockers cannot disappear silently. A later review must resolve or continue each one exactly once; terminal findings cannot be raised again.
  • A Judge update is all-or-nothing. Follow-up issues exist first, then one whole-Ledger write; exact retries converge.
  • Last-write-wins is detected, not trusted. Revision hashes, GitHub edit history, and dismissal pointers turn divergent writers or deletion into escalation.

What the validator means by valid

          
These are protocol claims the walkthrough is asking you to accept or reject.

        

      

      

        

          
ConcernProposed exact ruleFailure behavior

          
            
Round identityreview_key hashes PR, Contract digest, reviewed head, and delta base. The Ledger assigns the next contiguous human round number only when it accepts that key.An exact duplicate is an alias; a different payload under the same key is an integrity conflict.

            
Finding identityfinding_id hashes criterion/rule, path, stable symbol anchor, and failure mode. Evidence, wording, and line numbers may change without changing identity.Duplicate IDs in one review are invalid. A terminal ID appearing again is a forbidden re-raise.

            
EvidenceEvery point states actual behavior, expected behavior, consequence, one primary changed-line location, and at least one commit-pinned evidence URL.Malformed submitted reviews escalate; validation is intended to happen before submission.

            
Delta-onlyRound one covers the full base-to-head diff. Later rounds use the preceding accepted round head as delta_base_sha; every new or continuing point must touch that delta.A stale review is ignored as a round; an unchanged-code finding is a protocol violation.

            
DispositionEvery new point receives exactly one immutable outcome: blocking_now, follow_up, or dropped. Follow-up URLs exist before the Ledger write.A partial set is never written. A later outcome change is a fork, not an edit to history.

            
Prior blockersThe next accepted review names every blocker exactly once as resolved or continuation. A continuation keeps its original disposition and identity.Missing, duplicated, or terminal references make the review invalid.

            
Judge retryOne full snapshot carries a contiguous revision, previous digest, and content-derived mutation ID. Identical retry is a setter.Divergent siblings in GitHub edit history are detectable and escalate.

            
DiscoveryScan PR comments for exact sentinels, Ledger ID, and expected Judge Principal. Lowest comment ID wins only when every duplicate has the identical genesis. Each dismissed review points to the chosen URL/revision/digest.A divergent genesis, missing anchored comment, foreign edit, broken render, or broken hash chain escalates.

          
        

      

    


    

      

        

          
What to react to

          
The useful feedback is where the model feels dishonest, too strict, or too hard to read.

        

      

      
    
        
  • Does requiring each later review to explicitly resolve or continue every blocker feel like the right guard against silent disappearance?
    • 
        
  • Is a content-derived machine ID plus a short F-001 label clearer than asking the Reviewer to preserve a hand-authored ID?
    • 
        
  • Should stale reviews be ignored without consuming the review-round cap, leaving churn to the separate cost/no-progress policy?
    • 
        
  • Is escalation on a concurrent divergent edit preferable to attempting a three-way merge of two subjective Judge decisions?
    • 
        
  • Does dismissing every adjudicated REQUEST_CHANGES review, with a Ledger pointer as the dismissal message, feel like a sound anchor?
    • 
        
  • Can you understand why each sample was blocked, filed, dropped, or resolved from the readable Ledger without opening the JSON?
